# ADR-0015 — Production-studio layer

**Status:** Accepted · 22 November 2026

## Context

Second-round interview feedback asked NOVA to run a production studio end to end: several
simultaneous and multi-day shoots, artists as well as staff crew, scripts with versions and a scene
breakdown, a shoot-day screen for the set, client communication automation, budget plans, a
post-production review board, capacity planning, reports and an assistant that answers
operational questions — without fake functionality.

## Decision

1. **One more API module (`apps/api/src/modules/studio`)** on top of the operational core. It
   imports `DomainModule` and never the other way round. New collections: `Talent`,
   `TalentBooking`, `Script` (a creative document of kind brief/concept/script/storyboard/shot
   list), `ScriptVersion`, `Scene`, `ShootLogEntry`, `MessageTemplate`, `ClientMessage`,
   `BudgetLine`. Existing records gained optional fields (shoot call sheet and lifecycle, deliverable
   editor and internal review, feedback source, approval deadline, task → shoot link,
   notification resolution). Old documents without the fields read as their defaults.
2. **Shoot lifecycle gate.** `PLANNED → CONFIRMED → IN_PROGRESS → WRAPPED`. Confirming needs every
   blocking readiness item (approved script when one exists, location, crew, equipment, cast
   confirmed, no double booking); starting also needs a published call sheet; a future shoot
   cannot be started or wrapped. The rules are pure functions in `packages/shared/src/domain/studio.ts`.
3. **Artists are first-class resources in conflict detection.** Talent bookings join equipment
   bookings and crew calls in `ScheduleConflicts`; booking refuses overlaps and unavailable dates
   unless the overlap is acknowledged; moving a shoot checks artists too.
4. **Internal review before the client.** A deliverable must pass internal review before a version
   goes to the client; a client change request resets it. Client approvals carry a deadline
   (default three days) and are overdue after it.
5. **Communication automation is state-based and honest.** A listener on committed activity
   reconciles each record with the messages it should have (dedupe keys make it idempotent).
   Templates are OFF, DRAFT (a person reviews) or AUTO (queued). Delivery: Resend when
   `RESEND_API_KEY` and `MAIL_FROM` are set; otherwise the message is recorded as `SIMULATED` and
   the UI says nothing left NOVA. WhatsApp is always simulated. A message with an unfilled
   placeholder (for example `[reviewLink]`) can never be sent. Queued messages are dispatched by a
   one-minute timer on long-running servers and lazily when Communications is opened (serverless).
6. **Rule-based intelligence, labelled as such.** Script breakdown, artist/crew recommendations,
   readiness, capacity verdict and the assistant's demo mode are deterministic rules with their
   reasons returned. No model is claimed where none runs; with `ANTHROPIC_API_KEY` the Claude
   provider gets the same read tools.
7. **Permissions reuse the existing vocabulary** (no new permission keys, so existing role data
   keeps working): artists and shoot-day operations need `schedule:write`; scripts need
   `project:write` or `document:write`; script and internal-review decisions need
   `approval:decide`; client messages need `client:write`; budget plans need `project:write` or
   `finance:write` and are read only by roles that may see production costs.

## Consequences

- Existing databases need `pnpm db:setup` (new collections, indexes and validators); the seed does
  this. Message templates are created on first use when missing.
- Smart alerts are generated by a throttled sweep (at most every ten minutes per process) when the
  inbox or command centre is opened, deduplicated per user and condition.
